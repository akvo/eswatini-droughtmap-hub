# Feature Design Document

## Feature: Django Admin — Assign Activity Sector to Users (Sector Leads)

**Task ID**: TBD (Github Issue)
**Author**: Iwan Firmawan
**Date**: 2026-07-15
**Status**: Draft

---

## 1. Context & Problem Statement

```
Currently:
- SystemUser already has an `activity_sector` field (migration 0005), a bare
  IntegerField (null=True, no choices) commented "Marks a reviewer as a sector
  lead (create/edit own-sector drafts)."
- The whole enforcement chain around it already works:
    - v1_activity/permissions.py CanManageActivity — reviewer may edit only
      own-sector drafts (user.activity_sector == obj.sector).
    - v1_activity/serializers.py — reviewer may only create in their own sector.
    - v1_activity/views.py replace-file action — same own-sector gate.
- BUT the Django admin (v1_users/admin.py SystemUserAdmin) never exposes
  `activity_sector`. It is absent from list_display, list_filter, fieldsets, and
  add_fieldsets. An admin therefore has NO UI to assign a sector to a reviewer —
  it can only be set via the Django shell / raw ORM.
- Even if surfaced as-is, the field has no `choices`, so it renders as a
  free-form integer box: an admin could type 99 (no such sector) with no
  guardrail.

Goal:
- Let an admin assign / change / clear a user's activity sector from the Django
  admin, using a proper labelled dropdown (Food & Agriculture, Health &
  Nutrition, ...), with invalid values rejected.
- Make the sector visible and filterable in the user list.
- No change to the already-working runtime enforcement.
- Also fix a pre-existing admin inconsistency: `technical_working_group` is in
  `add_fieldsets` (create form) but missing from the edit `fieldsets`, so an
  admin cannot change a user's TWG after creation. Expose it in the edit form
  too (and in the user list), same as the sector.
```

This is a small, admin-only change. No new endpoint, no new model, no behavioural
change to the activity API. The "feature" is closing the assignment-UI gap for
two already-shipped user fields (`activity_sector`, `technical_working_group`).

## 2. Requirements

### User Acceptance Criteria
- [ ] An admin, in the Django admin user edit page, can pick a user's sector
      from a dropdown of the 8 defined sectors, or leave it blank (—).
- [ ] An admin can do the same when creating a new user.
- [ ] The user list shows each user's sector and can be filtered by it.
- [ ] Selecting an invalid sector is not possible (dropdown is closed-choice).
- [ ] An admin can change a user's `technical_working_group` from the edit page
      (not only at creation), and it appears in the user list.

### Technical Acceptance Criteria
- [ ] `SystemUser.activity_sector` uses `choices=ActivitySector.FieldStr.items()`.
- [ ] Importing the choices introduces no circular import
      (`v1_users.models` → `v1_activity.constants`; verified one-directional).
- [ ] A migration is generated for the `choices` addition (state-only; no data
      change) and applies cleanly on existing rows.
- [ ] Existing values (currently NULL or a valid int) remain valid; no data
      migration needed.
- [ ] Existing activity own-sector tests continue to pass unchanged.

## 3. Data Model Changes

### New Models

None.

### Modified Models

| Model | Change | Reason |
|-------|--------|--------|
| `SystemUser` | Add `choices=ActivitySector.FieldStr.items()` to existing `activity_sector` field | Renders a labelled dropdown in admin + adds `full_clean` validation of the value |

`technical_working_group` already has `choices` — it needs no model change, only
the admin exposure below.

### Admin config changes (`SystemUserAdmin`, no migration)

- `list_display`: add `activity_sector`, `technical_working_group`.
- `list_filter`: add `activity_sector`, `technical_working_group`.
- Edit `fieldsets` → "Permissions" group: add `activity_sector` and
  `technical_working_group` (the latter closes the create-only gap).
- `add_fieldsets`: add `activity_sector` (TWG is already there).

```python
# backend/api/v1/v1_users/models.py
from api.v1.v1_activity.constants import ActivitySector  # no cycle (see D-2)

    activity_sector = models.IntegerField(
        choices=ActivitySector.FieldStr.items(),  # 1..8 sector leads
        default=None,
        null=True,
        blank=True,
    )
```

### Migration Strategy

```python
# Auto-generated by `makemigrations` — AlterField on activity_sector.
# - choices are NOT stored in the DB, so this is a Django-state-only migration;
#   it issues no ALTER on Postgres (or a no-op) and is safe on existing rows.
# - Existing rows: NULL stays NULL; any previously-set int in 1..8 stays valid.
# - Rollback: reverse migration drops choices; field reverts to bare IntegerField.
#   No data loss either direction.
```

## 5. Decision Log

### D-1: Add `choices` on the model vs. only on the admin form

**Options Considered**:
1. Add `choices=ActivitySector.FieldStr.items()` to the model field.
2. Keep the model field bare; add a `ChoiceField` override only in a custom
   `SystemUserAdmin` ModelForm.

**Decision**: Option 1 — choices on the model.

**Rationale**: Same admin dropdown either way, but Option 1 also gives
`full_clean`/serializer-level validation everywhere the field is written, for
one keyword. Option 2 duplicates the sector list in a second place and leaves the
raw field unvalidated outside admin. Laziest correct = one keyword on the model.

**Impact**: One migration; `v1_users.models` gains an import from
`v1_activity.constants`.

### D-2: Circular-import safety

**Options Considered**:
1. Direct import `from api.v1.v1_activity.constants import ActivitySector`.
2. Lazy/local import or duplicate the sector map in v1_users.

**Decision**: Option 1 — direct top-level import.

**Rationale**: Verified the dependency is one-directional:
`v1_activity.constants` imports only from `v1_publication.constants`, and neither
imports `v1_users`. `v1_activity.models` imports `v1_users.models`, but models ≠
constants, so no cycle is formed. Duplicating the map would drift from the
canonical `ActivitySector`.

**Impact**: None beyond the import line.

### D-3: Should admins also carry an `activity_sector`?

**Options Considered**:
1. Sector is meaningful only for reviewers (sector leads); leave admins blank.
2. Force/validate that only reviewers may have a sector.

**Decision**: Option 1 (confirmed) — allow but don't require; no cross-field rule.

**Rationale**: `CanManageActivity` lets admins manage *any* sector, so an admin's
own `activity_sector` is simply inert at runtime. Adding a role-vs-sector
`clean()` rule is extra code guarding a harmless state. Best fit for current
conditions: ship without it; revisit only if admins-with-sectors cause confusion.

**Impact**: None. Field stays optional for all roles.

### D-4: Also expose `technical_working_group` in the admin edit form

**Options Considered**:
1. Keep scope to `activity_sector` only.
2. Fold in the fix — TWG is editable at creation but not afterwards.

**Decision**: Option 2 — include it.

**Rationale**: Same file, same fieldsets, one extra field name per list. TWG
already has `choices`, so it's admin-config only (no model change, no migration).
Leaving an admin unable to edit a user's TWG is a live gap worth closing here.

**Impact**: Adds `technical_working_group` to `list_display`, `list_filter`, and
the edit `fieldsets`.

## 8. Security Considerations

- [x] Permission model unchanged — assignment is behind Django admin, which
      already requires `is_superuser` (admin role auto-sets superuser on create).
- [x] Input validation improved — closed-choice dropdown + model `choices`
      rejects out-of-range sector ints that the bare field previously allowed.
- [x] No new attack vectors — no new endpoint, no new public surface.
